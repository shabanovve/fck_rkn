# Development Plan

## Goal

Build a repeatable test environment for an EU server, an RU server, and a test
client. The test environment is named `fck-rkn-test` and uses GCP. The
production environment is named `fck_rkn` and may run on any infrastructure
provider. `test_env_host` is the central orchestrator: it creates and prepares
the virtual environment (GCP VMs), invokes deployment agents to configure
services on those VMs, and invokes test agents to verify each milestone.
Services run in Docker on the VMs.

This plan describes a non-production test environment. Do not use production
credentials or expose an unauthenticated proxy to the public Internet.

## Development and deployment phases

### Phase 1: Test infrastructure and traffic filtering

Develop infrastructure and traffic-filtering behavior in the isolated
`fck-rkn-test` environment. `test_env_host` provisions and coordinates that
environment; the deployment agents configure the servers, and the corresponding
test agents verify each change. Do not use Phase 1 code or test credentials to
modify production.

### Phase 2: Production installation

Create production installation tooling only after the relevant deployment
behavior has passed its test-environment verification. Implement Phase 2 in
two ordered increments: deploy and verify `eu-server` first, then extend the
same production tooling to deploy and verify `ru-server`. The EU-only
increment must not run RU deployment actions or modify RU state. Before
implementing `prod_env_host`, complete and record an analysis of
`test_env_host` and its dependency path. The analysis must:

- Distinguish test-only responsibilities from production installation
  responsibilities, including provisioning, transport, test-client work,
  firewall resets, and cleanup.
- Determine the required and optional variables for `config/prod.env` and
  document them in the future `config/prod.env.example`, with validation,
  allowed values, value sources, and secret handling.
- Decide and document how `prod_env_host` will invoke and sequence
  `ru-server-agent`, `ru-server-test-agent`, `eu-server-agent`, and
  `eu-server-test-agent`. Account for each agent's runner and configuration,
  side effects, exit status, and failure behavior; do not assume test agents
  are safe to run against production without reviewing their checks.

The analysis must be completed before the production orchestrator is
implemented. Keep the analysis and its decisions in this plan. Do not treat
this planned work as an existing `prod_env_host` implementation or as proof
that the production configuration files already exist.

Production implementation is staged as follows. Before implementation,
decompose the work into small, ordered tasks by tracing the test orchestrator
one step at a time: task 200 creates a separate production implementation task
for each EU step that has a production equivalent (or documents why a
test-only step is excluded); task 201 does the same for RU after the EU task
breakdown is reviewed. Every generated implementation task uses a number
greater than 200, follows its dependencies, and covers only one
`test_env_host` step. Configuration-file creation/loading, settings
validation, each agent action/check, firewall operations, and failure handling
are separate task scopes where applicable. The decomposition tasks themselves
do not implement production behavior.

**Phase 2A — EU production deployment.** Implement the tasks produced by
task 200 to add production entry-point/configuration behavior for EU only. It
may read explicitly validated RU peer information when required to configure
EU, but it must not invoke RU deployment or test-agent functions, and must not
change RU state. Deploy EU services in dependency order and run only reviewed,
read-only EU health checks. Apply the EU guest firewall only after its inputs
are validated and EU services pass their checks. This increment must be
independently reviewed and verified before the RU implementation tasks
generated by task 201 begin.

**Phase 2B — RU production deployment.** Implement the tasks produced by
task 201 to extend the same production entry point and configuration with
RU-only settings and operations. Deploy RU services only after Phase 2A is
verified; use the dedicated EU Outline endpoint and access key required for
the RU client/forwarding path. Run only reviewed, read-only RU health checks,
and apply the RU guest firewall after RU services pass their checks. Never
reset the EU firewall or treat successful EU deployment as permission to run
RU actions in Phase 2A.

The two increments may be exposed as explicit subcommands or other
operator-visible stages, but the EU-only stage must be independently
invokable and must fail closed if it is asked to perform RU deployment.

**Operator entry point without arguments (task 245).** `prod-env-host` run
without arguments is the production counterpart of `test_env_host`: it ensures
a valid `config/prod.env` (starting the interactive configuration when it is
missing or invalid), then invokes `eu-server-agent`, `eu-server-test-agent`,
`ru-server-agent` and `ru-server-test-agent` in the same order as
`test_env_host`, each deployment followed by its check, stopping at the first
failure. Test-only steps are omitted. The RU decomposition is complete in task
201, but its implementation (tasks 301–318) is pending. Until Phase 2B is
implemented, the no-argument run performs the EU stage only and reports that
RU is not implemented; explicit single-step operations remain available.
Because Phase 2A and Phase 2B may run at different times, the Outline access
URL created for the RU connection must be retained or retrieved through the
approved operator-local `LocalSecretStore` described in `PROD_ENV_HOST.md` and
implemented by task 224; the in-memory-only handoff used by one continuous test
run is not sufficient. Do not place the URL in `prod.env`, command arguments,
logs, or an unprotected file.

### Task 88 analysis and decisions

The analysis of `src/fck_rkn/orchestration/test_environment.py`,
`src/fck_rkn/agent_config.py`, the agent modules, their remote scripts, and
the configuration examples produced the following findings and decisions.

#### Responsibility boundary

| Test-environment responsibility | Production treatment |
| --- | --- |
| Create/inspect GCP resources, validate the isolated test project, configure Cloud Router/NAT, create VMs and GCP SSH firewall rules, wait for IAP readiness, or stop test VMs | Exclude from `prod_env_host`. Production hosts are existing operator-managed servers; production access is SSH through `SshRunner`. |
| Build and load the patched Outline image on the test controller, provision `test-client`, create test access keys, and exercise the isolated test-client path | Do not provision a production test client or build/deploy an image implicitly. A production image-artifact distribution process and the production use of any Outline test key need separate decisions. |
| Remove the project firewalls before every test run, install policy only after the test-client stage, and save test inputs under `config/last_run/` | Never remove a production firewall as a reset step. In Phase 2A install the EU guest firewall only after EU services pass their checks; in Phase 2B install the RU guest firewall only after RU services pass theirs. Do not save credentials or production inputs under test run state. |
| Fetch live RKN, GitHub, Google, and Canonical network data and assemble GCP-specific VM service settings in the test orchestrator | Keep the RKN/GitHub/Canonical fetch and validation behavior reusable, but move it out of the GCP orchestration boundary before production use. Supply production-provider VM service addresses and egress ranges from validated production configuration; do not assume Google metadata, DNS, DHCP, or network ranges. |

`test_env_host` currently performs agent work by calling the Python agent
functions directly and injecting a `GcloudIapRunner`; it does not spawn the
four agent CLI executables. Follow that pattern in `prod_env_host`: load the
separate production settings, construct one `SshRunner` per server, and call
the relevant `eu_server`, `ru_server`, `eu_server_test`, and
`ru_server_test` functions with that runner. This avoids subprocesses
reloading `config/agents.env`, keeps the production configuration isolated,
and lets the orchestrator pass an Outline access URL in memory without
putting it in argv, environment variables, files, or logs. The server-side
agents remain provider-independent.

The current test entry point imports the GCP orchestrator and its dependencies:
GCP Compute client libraries and credentials, `gcloud` for IAP SSH, and
controller-side Docker for building/exporting the patched Outline image.
Production needs the shared settings, agent, and SSH-runner code plus the
OpenSSH client, but not GCP credentials, `gcloud`, Cloud NAT, or GCP API
libraries. The `google-cloud-compute` package is an optional `test-env` extra in
`pyproject.toml`; production installation does not need it. The production
entry point does not import `fck_rkn.gcp` or `test_environment`. The test-side image
build/export/load and local VM provisioning are likewise not production
dependencies; production image distribution is an artifact-management
decision.

#### Production configuration decision

`config/prod.env` is the production orchestrator's single source of
operator-supplied production values. It is separate from `config/test.env`
and from `config/agents.env` (which remains the configuration used by direct
agent CLI invocations). The production settings and template must be
validated before any remote command runs. Do not add credentials themselves
to either file; `SSH_KEY_PATH` names a protected key file supplied by the
operator or secret-management system.

The production configuration is introduced incrementally. In Phase 2A,
`config/prod.env.example` contains only the controller/SSH fields and EU
settings needed to deploy and verify EU, plus any explicit RU peer value
required by EU firewall rules. It must not require RU SSH credentials or RU
provider-service settings merely to run the EU-only stage. Phase 2B adds the
RU-only fields after its configuration requirements are implemented.

Implemented by task 244 (`prod-env-host configure`): `config/prod.env` is generated interactively. The
configuration step prompts
for the server address and SSH settings, connects over SSH, automatically
discovers the remaining settings that `eu-server` can report (read-only), and
explicitly prompts for any setting that cannot be discovered. The operator
confirms the validated values before the file is written. In the schema below,
"values come from the provider/network" means discovered over SSH where
possible, otherwise prompted.

The full planned schema, split by rollout stage, is:

| Variable | Requirement and value source |
| --- | --- |
| Phase 2A: `EU_SERVER_ADDRESS` | Required IPv4 or IPv6 address for the existing EU server, used for SSH from the controller and EU service binding. Obtain it from production network configuration and validate it as an IP address. |
| `SSH_USER`, `SSH_KEY_PATH`, `SSH_PORT` | Required SSH account, controller-side protected key path, and TCP port (1–65535; default 22). The account must have the permissions the deployment scripts require, including approved privilege escalation. The key material is never stored in the env file. |
| Phase 2A: `EU_METADATA_ADDRESS`, `EU_DNS_ADDRESSES`, `EU_DHCP_SERVER_ADDRESS`, `EU_NTP_ADDRESSES`, `EU_LOCAL_NETWORKS` | Required per-EU-host values for the metadata endpoint, resolver addresses, DHCP server, time servers, and local IPv4/IPv6 networks needed by the minimal-services firewall rules. Values come from the selected production provider/network. |
| `RU_SERVER_ADDRESS` | Required single RU server IP address in both phases. Phase 2A uses it only as peer input to the EU firewall; this does not authorize RU deployment. Phase 2B reuses the same value for RU SSH, Outline service binding, and RU firewall policy. Do not introduce a separate RU host or private-address setting. |
| Phase 2B: `RU_METADATA_ADDRESS`, `RU_DNS_ADDRESSES`, `RU_DHCP_SERVER_ADDRESS`, `RU_NTP_ADDRESSES`, `RU_LOCAL_NETWORKS` | Required RU host service values; keep them separate from EU values because the hosts may use different networks. |
| Phase 2B: `RU_PROVIDER_NETWORKS` | Required IPv4/IPv6 CIDR list for the production provider services that `ru-server` must reach on TCP/80 and TCP/443. Source it from the selected provider's published ranges and validate it against the crawler blacklist. |

Address-list and network-list values must have a documented, unambiguous
encoding (JSON arrays are preferred), strict validation, and a non-empty
requirement where the firewall depends on them. Add a detailed comment above
every variable in the eventual template explaining its purpose, allowed
values, and source. Do not add GCP project/zone/NAT values, `TEST_CLIENT_HOST`,
the test-only `other_host_address`, crawler probe values, or test credentials.
RKN, GitHub, and Canonical ranges remain live-validated inputs rather than
static secrets or values copied into this template; their shared fetch code
must be made usable outside `fck_rkn.gcp` before the production firewall
workflow is implemented. The production environment name is fixed as
`fck_rkn`, not a user-overridable target-project setting.

#### Agent sequence and test-agent safety

Use the following fail-fast order across the two rollout increments:

1. In Phase 2A, validate only the configuration required for EU and construct
   the EU `SshRunner`. Do not provision or reset servers, and do not construct
   or invoke an RU deployment runner/action.
2. Use `eu-server-agent` to configure EU services. After each deployment,
   run its corresponding service-only `eu-server-test-agent` health check
   before continuing. The Outline service must be healthy before creating a
   dedicated EU Outline key for the RU tunnel; store/retrieve it through the
   approved operator-local `LocalSecretStore` for the later Phase 2B run.
3. Apply and verify the EU guest firewall after EU services pass. Never remove
   or reset an existing production firewall. This completes Phase 2A.
4. In Phase 2B, validate the additional RU settings and construct the RU
   `SshRunner`; retrieve the EU Outline key through the approved operator-local
   `LocalSecretStore`. Do not repeat or reset successful EU deployment.
5. Use `ru-server-agent` to configure the RU Outline server, the EU Outline
   client and the Squid/MTProxy forwards using the protected EU key. Run the
   corresponding read-only RU service health and forwarding checks before
   continuing; apply and verify the RU guest firewall only after these checks.
6. Stop on the first failed action or check, identify the server, agent,
   action, and exit status, and return nonzero. Never log remote payloads,
   access URLs, firewall input containing credentials, or secrets.

Agent functions return zero on success and nonzero on command, validation, or
transport failure; the standalone agent CLIs use status 2 for invalid local
agent configuration. The test orchestrator wraps failures with step-specific
statuses and stops immediately. `prod_env_host` must preserve the same
fail-fast behavior and actionable step reporting; it must not turn an agent
failure into success or continue to firewall installation after a failed
service check.

Do not run the test-agent suites wholesale against production. The current
EU/RU firewall-policy checks create temporary network namespaces, routes, and
probe rules; crawler-source and VPN-client checks simulate sources and alter
test networking; rollback checks submit intentionally invalid firewall
updates; and tunnel-loss checks deliberately stop forwarding containers.
These are test-environment integration checks, not production health checks.
Production may run only explicitly allowlisted read-only health checks after
their behavior has been reviewed. Existing service health checks and the
blacklist timer/set inspection are candidates; firewall policy must not be
considered verified until a production-safe read-only verification mode is
defined and tested.

#### Gaps to resolve before production implementation

- `ru-server-agent` currently has no action to create or retrieve an access
  key for the RU Outline Server, despite the project requirement for user
  provisioning on both servers. Add and test that capability before
  production installation is considered complete.
- The production Outline image must be supplied as a reviewed artifact.
  The test-only controller build/export/load workflow is not a production
  artifact distribution or upgrade policy. Decision (task 217): a locally
  built archive identified by its SHA-256 digest, pinned in the tracked
  `artifacts/outline-image.sha256` and verified before transfer; no registry.
  See `PROD_ENV_HOST.md`, "Outline image artifact".
- The actual production provider, network addresses/ranges, SSH account and
  approved key source must be supplied by the operator before populating
  `config/prod.env`; do not substitute test/GCP values.

## Implementation sequence

### Orchestration responsibility

`test_env_host` owns the end-to-end lifecycle of the test environment:

- Create or reuse the required GCP virtual machines and prepare them for use.
- Give every GCP test VM outbound Internet access through Cloud NAT without
  assigning external IP addresses.
- Wait for VM readiness and provide the appropriate agents with access to
  their target VM.
- Run `eu-server-agent` and `ru-server-agent` to deploy or update services on
  their respective servers.
- Run `eu-server-test-agent`, `ru-server-test-agent`, and
  `test-client-agent` to verify the services and network paths at the
  applicable milestones.
- Remove the project firewall rules left by an earlier run once the VMs are
  running and SSH-ready, and install firewall rules only after `eu-server`,
  `ru-server` and `test-client` are configured and verified, in that order.
  Firewall checks reuse the test agents' code.
- Enforce the dependency order in this plan, stop on failures, and report
  which provisioning, deployment, or test step failed.
- Never treat a deployment-agent exit status as a substitute for running the
  corresponding test agent.

The agents perform their assigned work; `test_env_host` coordinates when they
run and on which VM. Provisioning, deployment, and validation are therefore
all part of the orchestrated workflow.

### 1. Create the GCP test project

- Create or select a GCP project for the `fck-rkn-test` test environment.
- Enable only the APIs needed for VM provisioning and access.
- Configure billing, IAM, and a dedicated test network before creating VMs.
- Configure Cloud NAT for the test VM subnet and region so VMs can access the
  Internet without external IP addresses.
- Record the project ID, region/zone, network, firewall policy, and resource
  budget in local operator configuration; never commit credentials.
- Keep GCP-specific provisioning and API calls in the test-environment
  orchestration layer; production service deployment and network policy must
  not require GCP. Agents depend only on the `RemoteRunner` interface; the
  test environment uses a GCP IAP runner, and production uses an SSH runner
  configured in `config/agents.env` (see `DEVELOPMENT.md`).

**Acceptance:** the operator can authenticate to the selected project, and
the required APIs, permissions, and network are confirmed without creating
unapproved resources.

### 2. Create `eu-server-agent`

- Implement a Python agent that connects to the existing `eu-server` over SSH.
- Initially, run `ping youtube.com` remotely and return a nonzero exit status
  if SSH or the command fails.
- Capture command output with secrets excluded from logs.

**Acceptance:** from the orchestrator, the agent connects to the intended VM,
runs the command, and reports its exit status and output. A ping result is
only an ICMP connectivity observation; it does not prove HTTP or proxy access.

### 3. Create `test_env_host` and provision `eu-server`

- Implement a Python orchestrator that queries GCP for a VM named
  `eu-server` in the selected project and zone.
- If it does not exist, create the approved lowest-cost suitable VM in the
  test network.
- Wait for the VM to become reachable, then invoke `eu-server-agent` on
  `eu-server`.
- Stop with an error if provisioning, SSH, or the agent command fails.

**Acceptance:** repeated runs reuse the existing VM rather than creating
duplicates; a missing VM is provisioned once and the first SSH/ping milestone
is reported accurately.

### 4. Deploy and test Squid on `eu-server`

- Extend `eu-server-agent` to deploy Squid in a Docker container on
  `eu-server`, listening on TCP port 3128. If its named container is already
  running with the current access policy, leave it unchanged instead of
  restarting it.
- Restrict access to the test network and explicitly approved test-client
  sources. Do not create a public open proxy.
- Configure the required host firewall rules inside the Ubuntu VM. GCP
  firewall rules may provide an additional boundary, but must not be the sole
  enforcement of the service's network policy.
- Create `eu-server-test-agent` to check TCP port 3128 and issue an HTTP
  request to `youtube.com` through Squid, recording the HTTP result.
- `test_env_host` runs `eu-server-agent` to deploy Squid, then runs
  `eu-server-test-agent` to test it. It fails the workflow if either step
  fails.

**Acceptance:** the test agent reaches port 3128 from an authorized test
source, a request through Squid succeeds, and unauthorized sources cannot use
the proxy.

### 5. Deploy and test Outline Server on `eu-server`

- Extend `eu-server-agent` to deploy the approved Outline Server container
  configuration on `eu-server`. Reuse an already-running container when its
  image and running state match the approved configuration; do not restart it.
- The EU Outline Server must be rebuilt from the official image with
  `outline-ss-server` patched so it accepts private target addresses (the stock
  server rejects them). This lets RU clients reach the private EU Squid
  endpoint through Outline. It removes the server's protection against
  requests to private networks; in production RU requests also reach the EU
  Squid through the tunnel at its private address on port 3128, and this risk
  is accepted.
- Provide and invoke a script to create a VPN user/access key after Outline
  Server is deployed and running, before client connectivity testing.
- Extend `eu-server-test-agent` to verify Outline Server health and test a
  client connection using the non-production access key created by the
  provisioning script.
- `test_env_host` runs `eu-server-agent` to deploy Outline, then runs
  `eu-server-test-agent` to test it. It fails the workflow if either step
  fails.

**Acceptance:** the server reports healthy and an authorized test client can
connect. Access keys are delivered through a protected mechanism and are not
written to source control or unredacted logs.

### 6. Provision `ru-server`

- Extend `test_env_host` to create `ru-server` in the same approved test
  project and network, using the approved VM sizing and access policy.
- Reuse the same idempotent provisioning, readiness, and SSH handling used
  for `eu-server`.

**Acceptance:** repeated runs do not create duplicate VMs, and only the
approved management and test traffic can reach the new instance.

### 7. Deploy and test the RU-to-EU proxy path

- Create `ru-server-agent` to deploy an Outline client in Docker on
  `ru-server` and establish the approved connection to `eu-server`.
- Forward the intended path to the EU Squid service on TCP port 3128, without
  direct Internet fallback.
- Create `ru-server-test-agent` to check port 3128 on localhost and issue an
  HTTP request to `youtube.com` through the configured path.
- `test_env_host` runs `ru-server-agent` to deploy the client and establish
  the path, then runs `ru-server-test-agent` to test it. It fails the workflow
  if either step fails.

**Acceptance:** the RU-side test reaches the EU Squid service through the
approved Outline-based path; arbitrary direct egress is denied; loss of the
Outline connection fails closed and recovery restores only the approved path.

**Technical validation gate:** Outline Server uses Shadowsocks and does not
by itself provide a general layer-3 VPN. Before implementing packet forwarding,
prove that the selected Outline client and forwarding design can provide the
required path to the EU private service on isolated test VMs. Do not silently
substitute another tunnel protocol or claim success based only on a simulated
route.

### 8. Deploy and test Outline Server on `ru-server`

- Extend `ru-server-agent` to deploy the approved Outline Server container
  configuration on `ru-server`.
- Provide and invoke a script to create a VPN user/access key after Outline
  Server is deployed and running, before client connectivity testing.
- Extend `ru-server-test-agent` to verify Outline Server health and
  authorized client access using the non-production access key created by
  the provisioning script.
- `test_env_host` runs `ru-server-agent` to deploy Outline, then runs
  `ru-server-test-agent` to test it. It fails the workflow if either step
  fails.

**Acceptance:** the RU Outline Server is healthy and an authorized test client
can connect; unauthorized access is rejected.

### 9. Provision and test `test-client`

- Extend `test_env_host` to provision a `test-client` VM in the isolated test
  network.
- Create `test-client-agent` to connect to `ru-server` using its Outline
  Server and a protected, non-production test key.
- `test_env_host` runs `test-client-agent` on `test-client` after provisioning
  the VM and completing the RU Outline deployment.
- Determine the actual route/interface address used by the approved design;
  check port 3128 at that address and issue an HTTP request to `youtube.com`
  through the intended proxy path.
- Ensure there is no direct-egress fallback and record the result of each
  check.

**Acceptance:** the test client connects through RU Outline, reaches the
approved proxy path, and successfully completes the HTTP check. Direct
Internet access outside the approved path is denied.

### 10. Define and enforce traffic restrictions

The authoritative requirements are in the "Firewall Requirements" section of
`DEVELOPMENT.md`. This step implements and verifies them.

- Enforce firewall rules only on `ru-server` and `eu-server`, with nftables
  inside the Ubuntu guest. `test-client` is an ordinary VPN client: install
  no firewall rules for this policy on it and add no special rules for it.
  IPv6 follows the same rules as IPv4.
- Resolve server addresses, provider metadata/DNS/DHCP addresses, the VPN
  listener and interfaces from provisioning/runtime configuration; do not
  hard-code VM addresses or interface names.
- Order rules in the input chain: loopback and established/related replies;
  minimal VM services; RKN crawler denial; project services; log and deny
  the rest. Log every denial with an `fck-rkn <host>` prefix
  (for example, `fck-rkn ru`), rate-limited to protect the kernel log.
- Coexist with Docker-managed chains; do not remove them.

| Source \ Target | `ru-server` | `eu-server` | Any other host / Internet |
| --- | --- | --- | --- |
| VPN client (any, including `test-client`) | VPN allowed; traffic inside the VPN addressed to `ru-server` unrestricted (including ICMP to the default route) | Denied | Only through the web proxy and MTProto proxy; all other traffic denied and logged |
| `ru-server` | Local traffic only | VPN only; direct web-proxy/MTProto denied | Minimal VM services only; all else denied and logged |
| `eu-server` | VPN only | Local traffic only | No restrictions |
| Any other host | SSH allowed; RKN crawlers and all other incoming denied and logged | SSH allowed from any address; VPN only from `ru-server`; RKN crawlers and all other incoming denied and logged | Not applicable |

Minimal VM services (loopback, established/related, DNS, DHCP, provider
services including metadata, snapd, NTP, ICMP) stay allowed on both servers,
as described in `DEVELOPMENT.md`. Google (AS15169) and Canonical (AS41231,
snapd) ranges are fetched and validated when the policy is applied and must
not overlap RKN crawler ranges.
Other package repositories, registries and monitoring endpoints stay closed
on `ru-server` except for maintenance or an approved address list.

**Default policy:** `ru-server` uses default deny for incoming and outgoing
traffic; `eu-server` uses default deny for incoming traffic and has no
outgoing restrictions.

**SSH:** TCP/22 is reachable on both servers; it must not be blocked based on
source address. IAP remains an approved but not the only SSH source.

**Blocking RKN crawlers on both servers:** use the general mixed IPv4/IPv6
blacklist in `C24Be/AS_Network_List/blacklists_nftables/blacklist.nft`, fetched
from that repository's `main` branch. The list is refreshed daily. Crawlers
are denied before the general allow rules, including SSH and VPN.
Each server runs the same local daily systemd updater and atomically replaces
its saved and active firewall rules only after fetching and validating a full
replacement. On `ru-server`, the output policy permits TCP/443 only to GitHub's
published API and web ranges from `api.github.com/meta`; those ranges are
refreshed transactionally with the crawler blacklist.

**Ru-domain blocking:** performed in Squid, not in the firewall.

Squid denies Russian domains (`.ru`, `.su`, `.рф`/`xn--p1ai` and subdomains)
and any destination given as an IP address literal (IPv4 or IPv6), for both
HTTP and `CONNECT`; only non-Russian domain names are allowed.

- Update firewall configuration transactionally: stage and validate the
  complete replacement rules and blacklist before activation. Require
  non-empty blacklist data with both IPv4 and IPv6 sets and at least one
  network, and validate nftables syntax before activation. Treat unavailable,
  empty, invalid, or un-installable replacement data as an update failure.
  On failure, retain the previous saved configuration, report the error,
  and keep the firewall running with its previous active rules; never leave
  a partially applied policy. If there is no previous valid configuration,
  fail without activating a partial one.

**Rollout:** while the log-only observation stage lasts, review the kernel
logs (`fck-rkn` prefixes) and add any missing minimal or project rules before
switching each rule to enforcement. GCP VPC firewall behavior is separate and
is not changed by guest nftables rules.

**Tests:** add network tests for each allowed path (SSH, VPN, proxies for VPN
clients, minimal VM services such as name resolution, time sync and DHCP
renewal) and each denied path (RKN crawler sources, direct traffic between
servers on proxy ports, VPN client traffic beyond `ru-server` such as ping to
external hosts, other incoming traffic). Verify that denials are logged.

**Acceptance:** only the flows above succeed; VPN clients reach only the
proxies beyond `ru-server`; both servers drop RKN crawler traffic; `eu-server`
has no outgoing restrictions; failed updates preserve the previous saved and
active rules and report an error.

## Cross-cutting implementation requirements

- When functionality is added to both servers, avoid code duplication. Put
  the common code in shared modules that both `ru-server-agent` and
  `eu-server-agent` call; only server-specific behavior and parameters stay
  in each agent. Share the corresponding test helpers the same way.
- Make `test_env_host` idempotent: detect existing resources, avoid accidental
  duplicates, and report every create/update action.
- Keep production deployment and firewall policy provider-independent. Agents
  configure and enforce required firewall rules inside the Ubuntu guest OS
  of each server; cloud-provider firewall rules are optional defense in
  depth, not a replacement for the guest firewall. Do not install these
  policy rules on `test-client`.
- Run the appropriate VPN user/access-key provisioning script from
